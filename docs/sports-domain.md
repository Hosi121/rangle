# ドメイン仕様

個人の一般ユーザー、団体の投稿アカウント、rangle運営を分離する。担当者の認証・管理、団体所有の生成・公開・削除は[担当者API](publisher-auth.md)へ接続済み。

## ユビキタス言語と確定事項

| 用語 | 意味 |
| --- | --- |
| 一般ユーザー `User` | 個人の視聴・声援・コメント・履歴の主体 |
| 団体アカウント `PublisherAccount` | 企業・団体の投稿主体。担当者アカウントと動画・生成ジョブを所有する |
| 団体担当者 `StaffAccount` | 団体が作成・管理する認証主体。一般ユーザーとは別のID・資格情報を持ち、団体内RBACに従う |
| 運営担当者 `RangleOperator` | rangle運営。旧adminに相当し、撮影・校正・同期・収録、基盤とアカウントの運用を担う |
| 試合 `Match` | 競技上の出来事。開催日時、参加チーム・選手、会場を持つ |
| 選手 `Athlete` | 競技に参加する人物。一般ユーザーや担当者のログインとは独立 |
| チーム `Team` | 競技上の集団。投稿団体とは独立し、選手の所属は時点に依存する |
| 会場 `Venue` | 試合・収録が行われる場所 |
| 大会 `Competition` | 試合をまとめる大会・リーグ等 |
| 収録 `CaptureSession` | 複数カメラの映像と、そのカメラ構成・校正版・同期情報を取得する単位 |
| クリップ `Clip` | 視聴・共有・声援の対象。試合や収録とは別の寿命を持つ |
| フォロー `Subscription` | 一般ユーザーが団体を継続して見るための無料の登録。担当者の所属・投稿権限とは独立 |

団体が担当者を持つ。保存先は `publisher_accounts/{account}/staff_accounts/{staff}`。一般ユーザーの `accounts/{username}` を複数団体へ所属させるモデルは採用しない。同じ担当者名・担当者IDでも団体が違えば別の認証主体とする。ログインは団体識別子・担当者名・パスワードで区別し、団体の共通パスワードは作らない。

投稿・生成ジョブの所有者は団体。操作履歴には運営／団体担当者の種別と、該当する団体ID・担当者IDを記録する。担当者を所有者にせず、一般ユーザーの声援履歴を団体へ移さない。運営の権限と団体内の役割は別スコープとする。

1試合に複数の収録、1収録に複数のクリップ・GSモデルを許容する。撮影はrangle運営の業務として扱う。試合と練習・デモは区別し、既存APIの `Event.kind=match` だけを試合と呼ぶ。未確認の選手・会場・投稿団体を推測で補完しない。

## 存続と削除

- 担当者の脱退・オフボーディングでは権限を失効させ、団体の動画は残す。
- 担当者0人の団体は存在してよい。「担当者不在」は団体の削除・停止とは別の状態で、運営が引継ぎを扱う。
- 団体を削除したとき、その団体が所有する動画を削除する。出演・参加しているだけの動画や、別団体の動画まで削除しない。
- 他の団体も参照する試合・選手・チーム・会場情報は、投稿団体の削除に連動して削除しない。

団体管理者が削除を要求し、rangle運営が確定・実行する。[削除API](publisher-auth.md#団体削除)は、公開停止・生成中ジョブの終了確認・所有資産の削除・CDN無効化を経て完了する。開始後にジョブが完了しても再公開しない。共有の元データと試合・選手・チーム・会場は保持する。声援・コメント・個人履歴も保持し、動画は削除済みとして参照不能にする。

## API権限

団体内RBACは「団体管理者 `administrator`」「投稿担当 `editor`」から始める。一般ユーザーは以下の管理APIを利用できない。団体IDは認証された担当者のスコープと照合し、URLやリクエスト本文だけから権限を付与しない。

生成APIは団体用 `/api/v1/publishers/{account}/generation` と、既存の運営用 `/api/v1/generation` を分ける。下表の生成パスは各prefixからの相対表記。

| API・操作 | 投稿担当 | 団体管理者 | rangle運営 |
| --- | --- | --- | --- |
| `GET /presets` | 団体に許可された入力のみ | 同左 | 運営用の入力を含む |
| `POST /jobs` | 団体に許可された入力で生成 | 同左 | 撮影・生成の運用 |
| `GET /jobs`・`GET /jobs/{job}` | 団体のジョブのみ | 同左 | 既存の運営所有ジョブ |
| `DELETE /jobs/{job}` | 団体のジョブのみ | 同左 | 同上 |
| `PUT /jobs/{job}/publication` | 団体の結果を公開・取り下げ | 同左 | 運営所有ジョブの公開・停止 |
| 担当者の作成・権限変更・無効化 | — | 団体内のみ | 引継ぎ等の運用 |
| 団体の削除要求・撤回 | — | 団体内のみ | 確定・実行・進捗確認 |
| 実験用 `/api/v1/private-scenes/**` | — | — | 運営専用 |
| 撮影構成・入力の登録、実行identity・GPU予算の設定 | — | — | 運営専用 |

団体向けにAPIを開いても、既存の許諾済み入力、資産検証、CSRF、全体の同時実行枠・予算・期限は維持する。ジョブ参照は操作した担当者ではなく団体で認可する。別団体のリソースは取得・更新できず、無効化した担当者と停止・削除中の団体は操作できない。

## 実装との対応

Goは `publisher.Account`・団体内の `StaffAccount`・権限を含まない `StaffPrincipal` を定義する。`Account.Allows` は上の団体RBACのドメインルールで、担当者管理と生成APIの認可へ接続済み。認可では公開プロフィールでなく現在の団体・担当者レコードを読み直す。旧 `AdminUser` / `is_admin` は互換のため残し、意味をrangle運営に限定する。

旧運営ジョブの `Owner` は従来の運営IDを維持し、担当者名の一致などで団体へ自動移管しない。新規団体ジョブは、認証・セッション、検索・冪等性・公開操作、private managerへの転送まで同じ団体スコープで検証する。

生成サービスは団体所有のジョブを `publisher_account_id`、作成主体を `created_by` に保存する。検索・冪等性の既存 `owner` キーは団体用の `publisher:{id}` とし、旧運営IDと分離する。同じ団体の後任者が参照・取消・公開でき、再送しても作成主体は変えない。運営用ジョブの既存キー・所有者は維持する。

運営の[入力割当API](publisher-auth.md#団体の生成公開)で確認済みpresetを団体へ割り当てる。DBの設定がない団体だけ、configの `publisher_accounts` を利用する。両方未設定なら運営専用。新規受付の台帳transactionでも許可を検査し、許可を外した後も既存ジョブの参照・取消は可能とする。公開時の団体プロフィールは受付時に確定し、データの出典・許諾・入力checksumは元のpresetを維持する。全団体で同じ同時実行枠・試行数・期限を共有する。

初版の公開 `context` は[架空の入力例](../testdata/sports/context.json)と同じ形で、運営確認済みcatalog／生成presetへ任意設定する。公開プロフィールに担当者・資格情報・権限・団体の内部状態を含めない。試合等のIDと表示名を持ち、同じ設定内で同じIDに矛盾する情報があれば拒否する。団体名・試合・選手・チーム・会場を検索と「概要」へ反映し、公開時点の情報を保持する。

本人の[声援履歴](accounts.md#声援の履歴)は交流DBへ保存する。仕様はGoの団体境界・RBAC・削除・オフボーディングのテスト、Firestore emulator、Go/Dart共通fixture、認証/管理画面のwidgetテストで確認する。実ブラウザ操作は利用者が確認する。
