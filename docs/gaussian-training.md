# 人物シーンでの動的Gaussian学習

UVG-GS BlueSquatを使い、時刻ごとの位置と不透明度を学習する小さな実装をローカルGPUで比較した。輪郭・時刻別の初期形状・深度監督により、人物領域の平均PSNRは16.169→20.206 dBへ改善した。未知視点の顔・手の崩れは残り、目標とする画質の達成とは判断していない。これはFreeTimeGSの公式実装の再現ではない。

## 素材と評価条件

[UVG-GS](https://tie-ultravideo.rd.tuni.fi/UVG-GS/index.html)の実写スクワット映像から、登録済みカメラ12台・source frame 56–75（25fps）を選んだ。GSデータとしての公開は2026年だが、同じシーケンスはUVG-VPCでも公開されている。撮影自体が2026年という意味ではない。[利用条件](https://tie-ultravideo.rd.tuni.fi/UVG-GS/UVG-GS_LICENSE_AGREEMENT.pdf)は非商用研究用途等に限定されるため、今回の入力画像・モデル・実験用コードは公開リポジトリへ含めていない。

学習8視点、評価4視点×20frameの80画像、960×803、黒背景、seed0、20,000 iteration、初期150,000・上限250,000 Gaussianを固定した。評価画像と評価depthは学習・初期化へ使っていない。配布されたカメラ校正は共通に利用し、world座標の正規化は学習カメラだけから求めた。以前のVRU Basketballとは素材が異なり、PSNRを直接比較して手法の優劣とはしない。

RGB・提供maskは元データから作成し、縮小後の焦点距離と主点を保持した。配布COLMAP画像と元画像の対応を確認し、今回の入力へ追加のundistortは適用していない。再取得したデータ・派生画像・校正・初期点群にはSHA256を記録した。

## 学習方法

[FreeTimeGS](https://arxiv.org/html/2506.05348v1)の時間付きprimitiveを参考に、各Gaussianへ位置・速度・中心時刻・持続時間を持たせた。

```text
position(t) = position + velocity × (t − centre_time)
opacity(t) = sigmoid(opacity) × exp(−0.5 × ((t − centre_time) / duration)²)
```

描画と勾配計算には外部依存のgsplat 1.5.3を使う。色は視点に依存しないRGBで、基準損失は0.8 L1＋0.2 SSIMと小さな空間scaleの正則化とした。論文のSH・知覚損失・periodic relocation等を含む全設定を再現したものではなく、論文の画質・速度を引き継ぐ主張はしない。

初期形状は学習用RGBDから作った。提供IR depthの座標をz軸まわりに180°回転してNUC座標へ変換し、提供transformでworldへ移した。別のRGB校正との合成一致を確認し、学習maskとの整合を使って50,000点へ整理した。RGB-onlyの再構成ではない。

最初の比較では、この同じ形状を3つの中心時刻へ配置し、同じ学習順序で輪郭lossの係数だけを0と0.1に変えた。輪郭lossは描画alphaと提供学習maskのL1である。

追加条件では、frame 56・65・75の学習用depthから別々の形状・色を初期化した。各50,000点、合計150,000点とし、RGB・mask・カメラ・評価画像・学習順序・iteration・点数上限は同じにした。初期化に利用する時刻別depthが増えているため、RGB-onlyで同じ効果を得た比較ではない。

最後に、同じ時刻別初期値へ全20時刻×学習8視点のdepthを追加した。IR点をRGBへ投影し、手前の正のZを残し、提供学習maskの境界を2pixel除いた疎な正解depthを作る。[gsplatのexpected depth](https://docs.gsplat.studio/main/apis/rasterization.html)と、正規化済みカメラZのL1へ係数0.1を掛けた。depthの全取得元・変換・SHA・学習視点のみであることを監査した。学習用depthの追加利用を含む比較であり、入力の増加とlossの効果を分離したものではない。

## 結果

以下は同じ80画像のfloat描画による平均。PSNRは高いほど、IoUは1に近いほどよい。

| 条件 | 全体PSNR (dB) | 人物領域PSNR (dB) | SSIM | 輪郭IoU |
| --- | ---: | ---: | ---: | ---: |
| RGB基準 | 20.979 | 16.169 | 0.8355 | 0.6070 |
| 上記＋輪郭loss 0.1 | 21.609 | 17.732 | 0.8536 | 0.8413 |
| 上記＋3時刻のRGBD初期化 | 24.155 | 19.715 | 0.8883 | 0.9271 |
| 上記＋全20時刻のdepth監督 | 24.645 | 20.206 | 0.8925 | 0.9384 |

最初の輪郭loss比較ではIoUが80/80画像で改善したが、人物領域PSNRは69/80で改善・11/80で低下した。顔・腕の内部の残像も残り、平均値の改善を全視点の画質改善や製品としての完成とは扱わない。保存PNGを別のCPU評価器で再計算しても傾向は一致した。

時刻別初期化でさらに改善した一方、未知視点の顔の崩れは残った。提供校正の光学精度や公開RGB/depthの補正工程まで独立に確認したものではなく、残る不具合を動的モデルだけに帰していない。以前のVRUへ同じ効果が出るかも未検証である。

診断用にframe 56だけの静的3DGSも6,000 stepで学習した。評価4画像の全体PSNRは27.088 dB、人物領域は19.230 dBで、顔の内部の崩れが残った。初期50,000点・最終64,546点と上表より少なく、iterationも異なるため原因を特定する対照ではないが、「時間変形だけが問題」という説明を採る根拠にはしなかった。

depth監督の候補は、基準比で人物領域PSNRが72/80画像で改善・8/80で低下した。時刻別初期化だけとの比較では59/80で改善・21/80で低下し、平均差は約0.49 dBだった。顔・手が必ず自然になる改善ではなく、ローカルでは基準と見比べる候補として扱う。

RTX PRO 500 Laptop（6GB）での最適化ループと、量子化snapshotの実サイズは次の通り。学習秒はcheckpoint保存を含み、環境準備・データ取得・評価は含まない。実行順・同一マシンの影響を統制した速度比較ではない。

| 条件 | 学習秒 | 20frame合計bytes | 初回frame bytes |
| --- | ---: | ---: | ---: |
| RGB基準 | 676.8 | 79,312,256 | 4,402,112 |
| ＋輪郭loss | 650.9 | 84,456,256 | 4,710,560 |
| ＋時刻別初期化 | 669.0 | 74,092,512 | 3,106,560 |
| ＋depth監督 | 741.1 | 74,625,408 | 3,107,712 |

最終点数は約237,000〜250,000、Torchのpeak allocatedは約341〜381MBだった。これはCUDA contextやブラウザを含む端末全体のメモリ量ではない。

## 配信・表示への接続

時間付きモデルを20個の`.splat` snapshotへ変換する。現在のUIはその離散frameを選んで視点を回す方式で、連続した4DGS動画の再生ではない。RGBA8・quaternion8の量子化を含むため可逆圧縮とは呼ばない。

基準とdepth監督の全frameを25fpsで連続取得するなら、約0.79・0.75 Gbps/人に相当する計算で、モバイル向けの配信帯域は未達である。HTTPキャッシュやCDNだけで端末までの取得量は減らせないため、画質の成立後は区間化した時間付きモデルの配布、品質別資産、端末での時刻評価を比較する必要がある。

実際に保存した`.splat`を読み戻し、同じカメラ・frame 0/10/19でfloat描画と比較した。人物領域PSNRは基準15.809→15.805 dB、depth監督19.342→19.341 dBで順位を維持した。この12条件の確認は全80画像評価の代替ではないが、今回の大きな内部残像をpackingだけで説明する結果ではなかった。

撮影カメラを再現するsceneには、省略可能な`camera.intrinsics`で縮小後のwidth・height・fx・fy・cx・cyを渡す。`referenceImageHeight`も学習時の高さ803へそろえる。仮想視点の見え方と、正解画像のある評価カメラの数値は分けて確認する。

Windows Edge / NVIDIA RTX PRO 500（ANGLE D3D11）で、390×844と1440×900のviewportを確認した。API→動画→自由視点→frame 0/10/19→orbit→動画復帰が候補・基準の両方で動き、JavaScript・WebGLエラーは0、離脱後のWorkerは0だった。同じbundleで既存VRU資産の回帰確認も行った。新データのdrawing buffer高さは803、VRUは270を保持した。これは機能確認であり、スマートフォン実機の速度・メモリ測定ではない。
