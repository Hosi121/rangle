# GS生成バックエンド

既存データセットの指定時刻から静的3DGSを学習し、自由視点ビューアで開ける。現在の対象は校正済みの複数カメラ画像で、一般的な単眼動画からの4DGS生成は対象外。

Webはフィードの「生成」、または `/demo/?generate=1` から開く。既存のID・パスワードでログインし、データ選択、生成、状態確認、結果表示まで進める。画面を閉じてもジョブは続き、再度開けば自分の履歴を確認できる。生成結果のリンクは直接自由視点で開く。

Go APIは既存のアカウントセッションを使う。Firestoreのトランザクションで全ユーザー共通の実行枠を一つ確保し、Vertex AIの東京Spot T4を起動する。配信APIとは別プロセスで学習するため、GPU処理がHTTPリクエストや動画配信を占有しない。

| 操作 | API |
| --- | --- |
| 利用できるデータセット | `GET /api/v1/generation/presets` |
| 作成 | `POST /api/v1/generation/jobs`、JSONは `{"preset":"…","request_id":"32桁の小文字hex"}` |
| 自分の履歴 | `GET /api/v1/generation/jobs` |
| 最新状態・結果 | `GET /api/v1/generation/jobs/{id}` |
| 中止 | `DELETE /api/v1/generation/jobs/{id}` |

POST・状態取得・中止はログインが必要。同じユーザー・request_idの再送は元のジョブを返し、追加起動しない。成功時のレスポンスには `viewer_url` と `scene_url` が付く。履歴一覧は保存済み状態を返すので、進行中のジョブは個別GETで更新する。

入力のURI・SHA256、コンテナdigest、GPU構成、期限はサーバー設定に固定する。ユーザーから任意のストレージパスやコマンドは受け取らない。設定ファイルを指定しなければ機能は無効。運用設定は[インフラの手順](generation-infrastructure.md)を参照。

## 計算予算と失敗時

この発表用環境では同時1件・1件30分・最大10試行。閲覧者の同時接続数と、学習の同時実行数は別に扱う。T4とCPUの構成を固定し、1試行あたり保守的に$2を予約して、承認されたGPU関連の$20枠に対応させる。これは請求額の実測や、請求の厳密なhard capではない。初回確認では試行数を1に設定する。失敗や中止でも試行枠は戻さない。

Vertexへの作成リクエストがタイムアウトしても、自動で再作成しない。ジョブラベルで照合してから状態を確定する。照合できない不明状態は実行枠を保持するため、運用者の確認が必要。中止要求だけでは実行枠を解放せず、終了状態を確認して解放する。

Vertexの30分制限に加え、workerにも作成時刻からの絶対期限を渡す。発表後の停止ワークフローでも、このアプリのラベルを持つ東京のジョブだけを中止する。Spotは空き不足や中断があり、即時実行や完了は保証されない。

## 学習と結果

workerはgsplatのDefaultStrategyとRGB、L1+SSIMで最大6,000 iterationを実行する。学習・評価カメラは分離し、評価画像は損失に使わない。ただし提供された校正と初期点群が評価カメラを含む可能性があるため、独立した汎化性能とは主張しない。

出力は32バイト `.splat` とgzipによる転送圧縮。色・不透明度・回転には量子化があり、浮動小数点モデルに対する可逆形式ではない。metricsにはfloat版と保存形式のPSNRを分けて記録する。gzip自体は `.splat` に対して可逆。

GCSにはファイルを新規作成限定で保存し、最後に `scene.json` を公開する。生成物は結果のリンクで確認できるが、画質確認前に公開フィードへ自動追加しない。生成クリップのコミュニティ機能は現在の静的カタログの対象外。

B300での実験は別の私的検証であり、この実行経路・資格情報・配信基盤には接続しない。

## 有効化と確認

対応するGo imageを先に配備し、SHA256を確認した入力とdigest固定のtrainerを用意する。最初のconfigは `attempts: 1` として、private catalogの内容SHA付きパスへ新規作成限定で配置する。Terraformでconfig SHA・IAM・停止定義を適用し、その後CIが新しい引数を引き継いだrevisionを検証・公開する。TerraformとCIのCloud Run更新は同時に行わない。

実ジョブの終了、metrics、評価画像、配信ファイルを確認してから、同じ台帳を保ったままconfigの試行上限を増やす。config変更は新しいSHAへ配置し、再度TerraformとCIで反映する。台帳の使用数や稼働中ジョブを消して枠を戻さない。無効化は既存ジョブの終了確認後に行う。
